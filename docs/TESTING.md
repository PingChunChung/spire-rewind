# Testing

This guide covers the offline test suite (the main path), the manual checks on the exported replay page, optional in-game testing on an isolated copy of the game, the acceptance checklist, fault injection, and what still has to be verified against Steam Cloud. Data format and test-channel details are in [FORMAT.md](FORMAT.md).

## What has been verified

On 2026-11-01 a first test on an isolated game copy (Ironclad, Ascension 0, both Spire Link and Spire Rewind loaded, Steam backend off) covered: both mods loading; checkpoints at room entry and room completion matching floor, HP, gold and deck; `choices.json` entries for a card reward, a shop purchase, a card removal and an event option; v2 decision snapshots; rewind from the pause menu and from the main menu, including the recovery checkpoint and `rewind.json`; the replayed fight reproducing 15/15 and 14/14 decision points (hands, draw piles, enemies, intents); the in-game export equal to the CLI export; a normal exit and continuing the run after a restart. The restyled rewind dialog and a rewind through its confirm button were checked the same day. Steam Cloud has not been tested.

## Offline tests

All offline tests run from the repository root and never read player data. `./test.ps1` runs exactly these, in this order, and stops at the first failure:

```powershell
dotnet run --project tests/SpireRewind.Core.Tests/SpireRewind.Core.Tests.csproj -c Release   # core tests, always
python -m unittest discover -s tests/python -p 'test_*.py'                                  # when python is installed
python tools/generate-sample-replay.py                                                      # when python is installed
node --test tests/js/test_replay_viewer.mjs                                                 # when node is installed
```

What each part covers:

- **Core tests** (`tests/SpireRewind.Core.Tests`, a console program that needs no game files): the checkpoint repository (ids, ordering, checksums, corrupt and truncated metadata, retention with and without an active run, symbolic links), `RestoreValidation`, `VerifiedSaveWriter` and `RestoreRecovery` with test doubles for the save interface, the `RestoreFault` latch, checkpoint stage labels, the test command channel's request validation, replay archive and snapshot checks, profile audit, the choice log, and the HTML exporter (escaping, CSP, envelope, warnings as fixed codes with no local path in the page).
- **Python tests** (`tests/python/test_export_replay.py`): `tools/export-replay.py` on a temporary folder: escaping and the three languages, replay header, checksum and identity checks, choice capacity, symbolic links, warning codes without local paths, NaN and Infinity rejection, and the command-line interface (sources unchanged, unsafe output paths refused). They use only the standard library and no network.
- **Sample page**: `tools/generate-sample-replay.py` rebuilds `docs/sample-replay.html` from fixed fake data; a failure here means the exporter or the viewer template broke.
- **Node tests** (`tests/js/test_replay_viewer.mjs`): the viewer's rendering and controls in a DOM harness, offline.

`test.ps1` does **not** build the game mod. The build against the game assemblies is a separate required check before a release:

```powershell
./build.ps1 -GameDir '<path to Slay the Spire 2>'            # Release build, dist/SpireRewind-<version>.zip, DLL path scan
./build.ps1 -GameDir '<path to Slay the Spire 2>' -Workshop  # also fills workshop/content/; fails without workshop/image.png (< 1 MB)
```

`build.ps1` fails when the built DLL contains the repository path, the user profile path or a `\Users\<name>\` fragment, in UTF-8 or UTF-16 and with either separator style (the embedded symbols are path-mapped to `/_/` by `Directory.Build.props`). The bare user name is deliberately not searched: the DLL contains ordinary words such as `user` and `system`, so an account with such a name would fail every build.

Also check the test command channel (the core tests cover its request validation; the rest is checked on the isolated copy): with `SPIRE_REWIND_TEST_MODE` unset or set to any other value no watcher node and no test files exist; with it enabled, a duplicate request UUID, an expired timestamp, a wrong snapshot id or index, corrupt JSON, path-like fields, reparse points, a combat action in flight, the enemy turn, and daily, multiplayer, replay or finished runs are all rejected.

## Offline replay page checks

Open [sample-replay.html](sample-replay.html) directly in a browser; no game is needed. The page is built from fixed fake data and is not evidence of a real recording. Check the per-floor timeline, the three curves, the choices on each floor, repeated attempts on the same floor, a missing snapshot, the AI reason text, and the in-game "replay from here" instructions on every checkpoint. Step through previous/next, play/pause, 1x/2x/4x, the end of the recording and replay from the start, and switch between Traditional Chinese, Simplified Chinese and English. At a 375 px viewport the page must stay usable without horizontal overflow. It must work fully with the browser offline and make no external resource requests.

The CLI exporter is `python tools/export-replay.py <profile folder> <run id> [--out <HTML path>] [--language zht|zhs|eng]`; the default output is `rewind/exports/` under that profile. Use a dedicated fixture or data from an isolated game copy. Verify that the source file names and SHA-256 hashes are unchanged after the export, that the output embeds the JSON and the script, and that it contains no native save payload. A corrupt or missing snapshot file must produce a warning; an invalid run id, path traversal and symbolic links must be rejected; a `</script>` or HTML string in the source data must not execute.

Older v1 snapshots must still load, and fields that v1 did not record must be shown as not recorded rather than as a real 0.

## In-game testing on an isolated copy

In-game testing is optional and uses an external harness that is not part of this repository. The harness prepares a disposable copy of the game with its own appdata directory, launches it on a private desktop so no window appears on the user's desktop, and drives it with Spire Link (`SpireLink.dll`, `SpireLink.json`, with `SpireLink.cfg` in the copy's own `%LOCALAPPDATA%\SpireLink`) as the driver mod; screenshots go through Spire Link's capture endpoint. It never touches the player's own install, mods, saves or cloud account, never reuses another test instance, and never replaces a normal exit with a forced kill. Only the current Spire Rewind build (`SpireRewind.dll` plus `mod_manifest.json` as `SpireRewind.json`) and a verified Spire Link build are installed into the copy. The game's mod consent screen appears before any DLL loads and a new account also has the early-access notice, the tutorial and the timeline disclosure, none of which Spire Link can operate, so the copy needs a test profile that has already passed them; that profile is a fixture, not player data. The Spire Link API key generated for the copy stays out of reports.

Before any functional test, confirm through Spire Link's authenticated `/v1/instance` endpoint and the isolation manifest that the PID, executable hash, Godot user root, account and save backend paths and port all belong to this copy, and that the platform is `None`. Hashing the original player profile before and after a session is read-only. Stop on any identity or path mismatch and let the game exit normally.

`SPIRE_REWIND_TEST_MODE=1` in the game process environment enables the file-based test command channel; the launcher preserves it, and removing the variable from the shell afterwards does not turn the mode off in a running process. Normal players and manual testers do not set it. The channel accepts `status`, `pause`, `list`, `restore`, `export`, `ui-open`, `ui-confirm`, `ui-close`, `ui-accept`, `save-and-quit`, `fault-inject` (main menu only: latches the restart-required fault as a failed rollback would, so the disabled native Continue can be checked; the process then has to be restarted) and the `replay-*` commands; request fields, receipts and result semantics are in FORMAT.md. Test mode is not a sandbox: any process with local file access can request a restore, so never enable it on real player data, and allow exactly one client per channel.

Rules for the channel: each command is one atomically published `command.json` with a fresh UUID `request_id` and a UTC `created_at_utc` inside the accepted time window; the channel must have no pending command; delete your own `command.json` only after a result with the same request id arrives. Receipts give at-most-once acceptance, not a guarantee of one successful execution. If a command times out, keep the command, result and receipt files, read the game log and `status`, and treat the outcome as unknown; never resend or retry under a new id while a restore may still be in progress. Archive or remove the channel only after the game has exited normally. The Spire Link HTTP token is used for authentication only and is not written into reports.

Spire Link has no save-and-quit action during a run. The channel's `save-and-quit` (after `pause` has opened the native pause menu) takes the pause menu's `ReturnToMainMenu` path, after which Spire Link's `menu_select quit` exits normally and the harness closes the private desktop. On builds without that command, send `WM_CLOSE` to the game window from a thread attached to the private desktop (the same as the window close button); do not use the harness's kill command instead of a normal exit.

`restore` is accepted only from the main menu or from the native pause menu and never interrupts a running action. A non-combat pause does not require `CombatManager.IsPaused` but does require a visible native pause UI, no running or queued action and no unfinished run save; a combat pause additionally requires a real pause in the player's play phase. `export` runs the same exporter as the in-game button and returns the HTML path. `ui-open`, `ui-confirm` and `ui-close` open the same rewind dialog as the button, enter the confirm screen for a checkpoint selected with the `restore` fields, and close it, for screenshots in the main menu or the pause menu. `ui-accept` presses the confirm screen's confirm button, exercising the dialog's own restore path; the restore is still in progress when the command returns, so poll `status` until it is no longer `busy`.

### In-game recording and export checks

In a normal single-player fight, play cards and stay on two or more screens; confirm the v2 snapshots record block, hand, played cards and intents. Take a card reward, buy a card, a relic and a potion, remove a card in the shop and pick an event option, then check `choices.json`. After a rewind to the same floor, a redone choice must be appended without mixing in other runs or profiles. Nothing is recorded while the mod is disabled or in multiplayer, daily or replay modes. After closing the game, export the same run with the CLI and compare its content and controls with the page produced by the in-game button. Whether every Harmony hook fires on each real choice branch, Godot button focus and layout with long paths are in-game items only.

### Rewind-and-replay check

Use one fixed seed, character and ascension. Complete the first fight and a second one, open the native pause through the channel, list the checkpoints and restore the first fight's room-entry checkpoint. Then replay that fight to the end and compare: the restored floor, HP, deck, metadata and rewind record, and the hand, enemies and intents at the start and after every decision. Playing only the same first card is not a pass. Do not treat a card-selection interrupt screen as the end of a fight. Refuse to start if the copy already holds a run; do not abandon or overwrite an existing run. Keep the result file and the separate Spire Link log as evidence.

### Replay library and decision snapshot player

The main menu "Combat replay library" lists the archives of each retained run. Version, commit, model hash, mod list, SHA-256 and snapshot checks must all pass; an older `.mcr` without snapshots reports `replay_snapshots_missing` and is not a playable snapshot file. Passing inspection does not mean native events were decoded or native playback is available.

Start a new single-player run in the isolated copy, finish one fight normally so a new archive is written, save with the native save and exit to the real main menu. Do not copy player files. Snapshots are recorded only when two consecutive frames show a stable idle state in the player's play phase and are deduplicated by `NextActionId` and content, so frames may be missing and the last frame is not necessarily the end of the fight. The check needs at least two frames; if there are not enough, keep the evidence and stop; do not fabricate data.

The `replay-*` commands need an external control root. Before launching the game set `SPIRE_REWIND_TEST_ROOT` to an absolute path that is not the Godot `user://` directory, not an ancestor or descendant of it, and contains no reparse point; the channel then lives in `test-control/` under that root. Both environment variables must be set before launch and removed from the shell afterwards; the running process keeps them. Without `SPIRE_REWIND_TEST_ROOT` the per-profile channel still works but every `replay-*` command is rejected. Confirm the isolation manifest, the `None` platform, the actual user root and the account path before running anything.

Send `replay-list` from the main menu to get the `run_id` and `replay_id`. Pick the newly recorded archive with at least two frames and choose an output path for the report that does not exist yet and lies outside both the control root and the whole Godot `user://` tree; verify the data root the audit reports before creating the output file. Then run `replay-audit-begin`, start the snapshot player with `replay-play`, and check the initial pause, next, previous, speeds 1, 2 and 4, resume and pause, polling `replay-status` to confirm the index advances while playing, holds while paused and pauses automatically at the end; after the end, resuming must restart from frame 0. Exit with `replay-exit` and finish with `replay-audit-end`. A pass has the player status `kind=decision_snapshots` and `native_playback=false`, and the audit result `unchanged`, `files_unchanged` and `memory_unchanged` all true with empty added, removed and changed lists. On failure or timeout keep the report, the channel files and the game log; do not mask an unknown result by resending. Waiting for playback to reach the end is bounded by the same timeout; a long recording at 4x can exceed 45 seconds, so pick a short fight or raise the limit.

`replay-audit-begin` requires the `None` platform and the real main menu; `replay-audit-end` may be attempted even when the main-menu condition no longer holds, so the session can be cleaned up and a result obtained. The audit hashes every file in the profile and account directories, including settings, prefs, recordings and snapshot sidecars, and compares the in-memory progress, prefs and settings; when the profile lies inside the account directory its files are counted in both scopes. Per-file hashing is not an atomic file-system snapshot and cannot rule out background writes by the platform or other processes; any difference or read failure is a fail. A `None` platform result says nothing about Steam Cloud, and native playback isolation still has to be delivered and verified separately.

## Acceptance checklist

For every item record the game version, the DLL SHA-256, the isolated root, the steps, expected and actual results, screenshots and the hashes of the relevant files in a dedicated evidence folder. Never report a build-only or `None` platform result as a Steam Cloud pass.

| Case | Steps and pass condition |
| --- | --- |
| Loading and coexistence | Both mods load without Harmony exceptions; Spire Link observes and operates normally. Then disable only Spire Link in the copy's in-game mod manager, exit normally, relaunch with the same launcher and confirm from the log that only Spire Rewind is loaded and usable. Keep the Spire Link files in place for the launcher's static checks; this pass does not require Spire Link endpoints, only the manifest, process and isolated paths in the log. |
| No current run | The main menu shows only the rewind settings entry and no checkpoint list; no fake current save is created. |
| Automatic saves | Start a new single-player run, pick a map node, win a fight, complete the Ancient event. Every successful native save produces a new meta/payload pair; a failed native save produces no checkpoint. |
| Room-entry labels | After floor 5, enter a shop on floor 6: the list shows a floor 6 shop marked as about to be entered; an unknown node shows as unknown without drawing RNG early. Also verify the first floor of the next act. |
| Room-completion checkpoint | After a victory `pre_finished_room` is kept and a restore does not restart the finished fight; to replay it, pick its room-entry checkpoint. |
| Rewind from the pause menu | In the next fight open pause, choose rewind, cancel: the save is unchanged. Confirm instead: the current run exits, the single-player run is replaced and the chosen stage loads automatically. Repeated clicks do not submit twice. |
| Rewind from the main menu | Exit normally to the main menu, pick a checkpoint from the rewind entry; it loads without pressing Continue first and does not load stale data cached by the main menu. |
| Determinism | Record the pre-fight hand, enemies and action order; rewind to the same checkpoint and compare draws and enemy intents under the same actions. Different action branches need not match. Check the run RNG and the player RNG. |
| Replay archives | Test a win, a loss and a normal mid-fight exit once each; whenever the latest recording changes, a new `.mcr` and sidecar are written and a replay of the same floor does not overwrite the previous one; check `combat_completed`, `run_ended` and `interrupted` respectively. Actual playability of the recording is verified by the replay research track. |
| Settings and language | Traditional Chinese, Simplified Chinese and English can be switched and persist across restarts. With the switch off no files are added and rewind is unavailable; after switching on, the next native save adds the first file. Check missing CJK glyphs, long English strings, 960x540 and 1920x1080, mouse, keyboard and controller focus, and scrolling. |
| Retention policy | Set N=2, complete three runs or generate three with a dedicated fixture; only the two most recent remain and the current run is never deleted. Test N=1, lowering N, lowering N with no run in progress (the newest N runs remain), several checkpoints on one floor, the same seed with different start times, and separate profiles. |
| Profile switch during a restore | Through the test channel, start a restore and, while it is in progress, open the profile screen and pick another profile. The switch is refused (the game log shows `profile_switch_refused_during_rewind`), the restore finishes in the original profile, and the other profile's `saves\` folder is unchanged. |
| Statistics and marking | Compare progress and history before and after. A rewind itself changes neither; replayed fights may increase encounter and enemy win counts through the native flow. The default mark is written only to `rewind.json`; unticking the mark still increases `restore_count` and an existing mark is not removed. |
| Rejections | Daily runs, multiplayer host and client, replay, finished runs, a different game version, schema or mod version, another run or profile, a corrupt payload or hash and an invalid id are all rejected and the current save is not replaced. Prepare these fixtures only in the copy. |
| Local restart | After a successful rewind exit normally and launch the same copy again; the rewound run continues and the checkpoints and recordings stay in that profile's `rewind/`. |

## Fault injection

These cases need a test build or test doubles for the save interface; never cause a full disk, a disconnect or a permission change in the player's real directory. Keep the preparatory fixtures and exit normally after each test. The core `VerifiedSaveWriter` and `RestoreRecovery` are covered by tests with doubles; the items below verify the real Godot lifecycle.

1. The first write of the target save fails, fails silently, the remote publish fails, the remote read-back differs or reports `persisted=false`: loading stops and the original save is recovered. When both local and cloud recovery succeed, the screen states clearly that the player can return to the main menu and continue.
2. The target write succeeds but the second save from `IncrementNumReloads` inside `SetUpSavedSingleplayer` fails. State is already set while the shared manager is not initialised; even if `CleanUp` fails, the original save must still be recovered and a restart prompt shown; the game must not continue in an incomplete old scene.
3. The first `ReturnToMainMenu` or a later `LoadRun` or scene cleanup fails. If the first exit fails the original save has not been replaced yet, and the player must still be told to exit normally and restart; on later failures keep the `before_restore` backup and recover as far as possible.
4. The cloud write of the target fails and the cloud recovery of the original also fails. The screen must not claim success; it must tell the player to stop playing and keep the backup, and the diagnostic message must contain the backup checkpoint id. From that moment `RestoreFault` is latched: the Rewind dialog shows the fault and the backup id at the top, `RestoreService.CanRestore` is false, the test channel answers `restart_required`, and only a restart of the game clears it (core test `RestoreFaultTests`).
5. Writing `rewind.json` fails. When the target is already loaded, show "loaded but the record failed" rather than claiming the player is still in the original run.
6. Place fixtures in the folder with a missing meta file, truncated JSON, oversized files and a junction. The list skips incomplete entries, a restore rejects corrupt ones, and retention cleanup does not follow the link target.

## Steam Cloud manual acceptance

All tests so far ran with the Steam backend off (`--force-steam off`, `None` platform). They prove nothing about Steam uploads or about synchronisation at the next launch. This section is the manual test that still has to be done, by a person signed in to Steam, before the Steam Cloud warning can be dropped from the README and the Workshop page. It cannot be automated by the harness: the harness never signs in to Steam.

**Account and setup.** Use a Steam account whose cloud saves for the game you can afford to lose, on a machine where the game is installed through Steam with Steam Cloud enabled for the game (Steam > game properties > General > Steam Cloud). Install the mod one way only (Workshop subscription or `mods/SpireRewind/`), start the game, allow mods. Modded play uses `modded/profileN`, so the account's unmodded saves are not part of the test, but they share the cloud quota. Write down the game version shown in the main menu and the SHA-256 of the installed `SpireRewind.dll`.

Where to look: the profile folder is `%APPDATA%\SlayTheSpire2\steam\<steam id>\modded\profile<N>\` (`saves\current_run.save`, `rewind\`). The game log is `%APPDATA%\SlayTheSpire2\logs\` (or the folder the game shows in its settings); Steam's own sync log is `Steam\logs\cloud_log.txt`. The mod logs every restore step and failure with the prefix `[Spire Rewind]`.

Each case records: steps, expected and actual result, the game log excerpt, the `before_restore` checkpoint id, and the SHA-256 of `current_run.save` before and after. A case passes only when every "Pass when" line holds.

| # | Case | Steps | Pass when |
| --- | --- | --- | --- |
| C1 | Normal restore, then sync and restart | Start a single-player run, play two rooms so two or more checkpoints exist, exit to the main menu, wait until Steam's sync icon (and `cloud_log.txt`) show the upload finished. Note the SHA-256 of `current_run.save`. Main menu > Rewind > pick the first room-entry checkpoint > confirm. | The run loads at that floor. The dialog closes without an error. `rewind\runs\<run id>\checkpoints\` has a new `before_restore` checkpoint whose `run.save.json` has the noted SHA-256. `current_run.save` equals the chosen checkpoint's `run.save.json` except for `num_reloads`. No `[Spire Rewind]` error in the log. |
| C1b | Same, after exit and relaunch | Continue C1: play one more room, exit the game normally (quit to desktop), wait for the Steam sync to finish, start the game again, Continue. | The rewound run continues (same floor and deck as before the exit, plus the extra room). Steam showed no sync conflict dialog. `cloud_log.txt` shows `current_run.save` uploaded once per save and no download of an older version. `rewind\` files do not appear in the cloud (the Steam client's cloud file list for the game, or `userdata\<id>\<app id>\remote`, holds no `rewind` folder). |
| C2 | Local and cloud copies differ before the rewind | Make the cloud copy newer than the local one: with the run in progress on machine A, exit, let it sync; on machine B (or after `Steam Cloud` was off on A for a while) play one room and sync; then back on A, with Steam Cloud on, start the game and resolve nothing yet. If only one machine is available: turn Steam Cloud off, play a room, exit, turn it back on, start the game, and if Steam asks, keep the cloud version so that the local file is the older one. Then open Rewind and confirm a checkpoint. | The restore is refused with `cloud_not_in_sync` before anything is written: `current_run.save` keeps its SHA-256, no `before_restore` checkpoint is created, the run continues as before. |
| C3 | Offline | Put Steam into offline mode (Steam > Go Offline), start the game, open Rewind and confirm a checkpoint. | Either the restore completes and the dialog reports success, or it is refused; in both cases `current_run.save` is a verified file (the chosen checkpoint or the original) and the log says which. After going online again and relaunching, Continue loads the same run the dialog reported; if Steam shows a conflict dialog, note which version it offered and keep the local files. |
| C4 | Steam Cloud disabled for the game | Turn Steam Cloud off in the game's Steam properties (and, separately, the account-wide setting), start the game, rewind. | The restore completes locally; the dialog reports success; no cloud write is attempted (nothing new in `cloud_log.txt`). Turn Steam Cloud back on, relaunch; Steam may ask about a conflict: keep the local files; the rewound run continues. |
| C5 | Game version differs from the checkpoint | Use a checkpoint taken on another game version (a run started before a game update, or a `meta.json` whose `game_version` was edited in a copy made for this test). | The dialog lists the checkpoint and the confirm screen refuses it with `game_version_mismatch`; nothing is written. A real update also shows the untested-version notice at the top of the dialog. |
| C6 | Interrupted restore, then restart | Start a rewind from the pause menu and end the game process while the dialog still says the restore is in progress (Task Manager; this is the one case where a forced kill is the test). Start the game again. | Continue loads either the original run or the chosen checkpoint, never a partial file (the game loads it without a save-file error). `rewind\` has the `before_restore` checkpoint. If the dialog had reported that the original was recovered or that a restart is required, the loaded run matches that message. Steam shows no conflict, or a conflict in which keeping the local files gives a playable run. |
| C7 | Quota | Only if the account's cloud quota for the game can be filled (Steam shows usage in the game's cloud settings). With the quota almost full, rewind. | The restore is refused or reports a cloud failure with the original save recovered; the dialog never claims success while `cloud_log.txt` shows a failed upload. |

Until C1, C1b, C2, C3, C4 and C6 have passed, the README, `packaging/README.md`, `CHANGELOG.md` and the Workshop description keep the sentence that Steam Cloud has not been tested, and any report lists the cloud items as unverified. A successful Steam API read-back inside the restore only shows that the content seen through that interface matches; whether the server finished the upload is decided by C1b.
